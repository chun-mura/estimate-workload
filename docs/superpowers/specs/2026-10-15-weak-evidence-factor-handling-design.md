# 根拠の弱いAI支援係数の扱い（案）

- 状態: 提案（未実装）
- 日付: 2026-10-15
- 前提: PR #2（AI支援の感度の幅 `ai_sensitivity`、0.12.0）がマージ済みであること
- 対象: `scripts/estimate_calc.py`（`cmd_calibration`、`cmd_pipeline`）、`skills/record/SKILL.md`、`skills/new/references/ai-assistance-factors.md`、`skills/new/references/report-template.md`、テスト

## 背景

AI支援の既定係数のうち、カテゴリに特化した研究で裏付けられているのは `backend-api` だけである。`frontend-ui`・`test-only`・`db-migration`・`infra` は判断で置いた値で、当面は外部の研究で補える見込みがない（2026-10-15 の追加調査）。

そのため、根拠の弱い係数は「より良い研究を探す」ことで改善するのではなく、次の3つで扱う必要がある。

1. 幅を持たせたまま判断に使う。
2. 自社の実績で早く、かつ偏りなく置き換える。
3. 期限を決めて見直す。

現在の実装には、この3つについて次の問題がある。

1. **学習した係数への切り替えが急すぎる。** AIあり・なしの実績が各3件そろうと、既定値は使われなくなり、学習した値に全面的に切り替わる。3件の中央値の比はばらつきが大きく、1件の外れ値で係数が大きく動く。
2. **実績の取り方に偏りが入りやすい。** `/estimate:record` は実績の時間を利用者に尋ねるだけである。
   - METR 2025 では、体感（20%速くなった）と実測（19%遅くなった）の向きが逆だった。記憶で答えた時間で学習すると、AIの効果を過大に見積もりやすい。
   - AIを使う作業を利用者が選ぶと、簡単な作業にばかりAIを使うことになり、効果が大きく見える（選択バイアス）。
3. **既定係数に見直しの期限がない。** ツールの世代が変わると効果も大きく変わる（METR 2025 → 2026）が、係数がいつ時点の根拠に基づくのかが記録されていない。

## 根拠

| 論点 | 根拠 |
| --- | --- |
| 体感と実測は食い違う | METR 2025（arXiv:2507.09089）。体感では約20%速くなったが、実測では19%遅くなった |
| 少ない件数での推定は不安定 | 既存の `LOW_SAMPLE_THRESHOLD = 10`。参照クラス補正も10件未満を参考値として扱っている |
| 判断で置いた値は一般的な研究の範囲に収める | 2026-10-15 の追加調査。カテゴリに特化して時間を比べた研究は見つからなかった |
| 外れたときの損失は非対称 | 社外へ約束した見積もりを超過すると赤字になる。余った場合の損失は小さい。P80 をコミットの水準にしている既存の方針と同じ考え方 |

## 提案

### A. 学習した係数を、件数に応じて既定値と混ぜる（縮小推定）

「各3件で全面的に切り替え」をやめ、件数が増えるほど学習した値に寄せていく。

```
n        = min(AIありの件数, AIなしの件数)
w        = n / (n + N0)                          # N0 = 事前分布の強さ（既定 5）
factor   = exp( w * ln(learned) + (1 - w) * ln(default) )
```

- 係数は比なので、対数の上で混ぜる。
- `N0 = 5` なら、n=3 のときは学習値の重み 38%、n=10 のときは 67% になる。
- `pipeline` の `ai_factor` は、`source` に `blended` を加え、`learned`・`default`・`weight` も返す。
- 学習値を計算し始める件数（各3件）は変えない。

### B. 感度の幅を、件数に応じて狭める

- 今の `ai_sensitivity` は、既定係数のタスクが1件でもあれば出し、全タスクが learned になると出さない。
- これを、A の重み `w` に合わせて楽観・保守の係数を中央に寄せる方式に変える。
  - 楽観の係数 = 中央 + (1 − w) × (既定の楽観 − 既定の中央)。保守も同じ式で計算する。
- n が `LOW_SAMPLE_THRESHOLD`（10）以上になったカテゴリは、幅を出さない。

### C. 実績を記録するとき、客観的な記録を求める

- `/estimate:record` で、実績をどこから取ったかを尋ねる。選択肢は「時間の記録（タイムトラッキング・PRやチケットの期間など）」か「記憶」の2つ。
- 履歴の記録に `actual_basis: "tracked" | "recalled"` を追加する（任意の項目。旧レコードは `null`）。
- `calibration` は、AI係数の学習に `tracked` の実績だけを使う。参照クラス補正では従来どおり全件を使う。
- 選択バイアスについては、record と new の SKILL に次の運用上の注意を書く。計算では補正しない。
  - 同じ種類の作業で、AIあり・なしを交互に割り当てる。
  - AIを使うかどうかは、作業の難易度で決めない。

### D. 既定係数に見直しの期限をつける

- `ai-assistance-factors.md` の表に「根拠を確認した日」を加える（初期値 2026-10-15）。
- 確認日から6か月を超えた状態で `/estimate:new` を実行すると、レポートの `## リスク` に「既定係数の根拠が古い」を1行加える。
  - 判定はスキルではなく CALC が行う。`pipeline` の入力に `factor_reviewed_on` を渡し、警告を返す。

### E. 用途ごとに使う値をレポートに明記する

- レポートの雛形の「AI支援の感度」表の下に、次の1行を固定で置く。
  - 「社外への見積もり・契約には、根拠の弱いカテゴリを含む場合は保守の P80 を、社内計画には中央の P50 を使う。」
- 最終判断は担当者が行うことも併記する。

## 影響

- **出力が変わる。** A により、各3件を超えたばかりのカテゴリでは、AI支援の値が既定値寄りになる。
- **スキーマが変わる。** C で履歴に任意の項目が増える。
  - 意味を変える項目ではないので、`SCHEMA_VERSION` を上げるかどうかは要検討。リポジトリの CLAUDE.md の規約は、既存の項目の意味が変わる場合に限って上げるよう定めている。
  - 旧レコードは `null` として扱い、AI係数の学習から外れる。そのため、既存の学習済み係数は既定値に戻る可能性がある。
- **テスト**: `calibration`・`pipeline` の係数の出どころ、感度の幅の縮み方、record の契約テストを追加・変更する必要がある。
- **バージョン**: `scripts/`・`skills/` を変えるので、マイナーバージョンを上げる。

## 決めること

1. A の `N0`（事前分布の強さ）を 5 にするか。値を大きくするほど既定値に長く引っ張られる。
2. C で、旧レコード（`actual_basis` が `null`）を AI係数の学習から外すか、`recalled` として扱い警告付きで使うか。
3. D の見直し期限を6か月にするか。
4. A〜E を一度に実装するか、C（記録の改善）を先に出すか。C はほかの提案と独立していて、データの質に直結する。
